# WM-Forecast — AI-Powered Demand & Inventory Console

A Walmart weekly-sales forecasting app that's grown into a small end-to-end
decision-making system. Five pieces work together on top of the original
forecasting pipeline:

1. **Deep Learning** — an LSTM sequence model (alongside the original XGBoost
   baseline) forecasts demand from raw sales history.
2. **Explainable AI (XAI)** — SHAP shows why the model predicted what it did,
   feature by feature.
3. **RAG** — a retrieval-augmented "Ask Walmart AI" assistant answers policy
   questions grounded in real documents (inventory policy, supplier rules,
   store guidelines, stock thresholds, holiday calendar, product info).
4. **Agentic AI** — an agent combines the forecast, inventory, supplier
   lead-time, and policy tools into a reasoned reorder decision per store.
5. **Automation** — a daily scheduled job runs the agent across every store
   and surfaces stockout-risk alerts.

## Setup

Requires Python 3.10+.

```bash
cd walmart-forecast-app
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

This installs Flask, the ML stack (scikit-learn, XGBoost, PyTorch, SHAP),
`rank-bm25` for RAG retrieval, `APScheduler` for automation, and the
`anthropic` SDK (optional — only used if `ANTHROPIC_API_KEY` is set; see
**Optional: LLM-generated answers** below).

## 1. Build the models (run once, or whenever Walmart.csv changes)

```bash
python3 scripts/preprocess.py   # -> data/train_features.csv, test_features.csv, full_features.csv
python3 scripts/train.py        # -> model/best_model.joblib (XGBoost) + metrics files
python3 scripts/train_lstm.py   # -> model/lstm_model.pt + metrics appended to model_comparison.csv
```

`train_lstm.py` takes a couple of minutes on CPU (60 epochs over ~4.6k
sequences). You should see something close to:

```
                       Model       MAE      RMSE  MAPE (%)  WAPE (%)
0  Naive (last week's sales)  50361.57  75313.17      4.89      4.85
1          Linear Regression  58795.67  81231.81      6.25      5.66
2              Random Forest  42788.17  61521.01      4.18      4.12
3                    XGBoost  38008.09  54283.86      3.88      3.66
4                       LSTM  51517.13  73689.11      5.04      4.96
```

XGBoost currently wins on this dataset's size (~6.4k rows) — its hand-built
lag/rolling features give it an edge that a from-scratch sequence model
needs more data to close. Both models are served; the Forecast page lets you
compare them live per store.

If you skip step 3, the app still runs fine — it just serves XGBoost only and
hides the LSTM option (`lstm_is_available()` checks for the artifact files).

## 2. Run the app

```bash
cd app
python3 app.py
```

Open **http://localhost:5000** in your browser. First load takes ~20-30
seconds while PyTorch/SHAP/the model artifacts load into memory — subsequent
requests are fast.

To retrain with a new/updated `Walmart.csv`, drop the new file into
`data/Walmart.csv` and re-run step 1 — the running app picks up the new
model on restart.

## API (used by the frontend, also usable directly)

**Core forecasting**
- `GET /api/model-metrics` — model comparison table + metadata (now includes LSTM)
- `GET /api/feature-importance` — importance per feature (XGBoost)
- `GET /api/actual-vs-predicted` — test-period actual vs predicted, aggregated by week
- `GET /api/holiday-effect` — avg sales holiday vs non-holiday
- `GET /api/stores` — list of all stores with summary stats
- `GET /api/stores/<id>/history` — full sales history for a store
- `GET /api/stores/<id>/actual-vs-predicted` — test-period accuracy for a store
- `GET /api/stores/<id>/latest-state` — most recent known feature row for a store
- `POST /api/forecast` — body `{"store": 1, "weeks": 4, "model": "xgboost"|"lstm", "Holiday_Flag": 1, ...}` → recursive multi-week forecast
- `GET /api/stock-plan?safety_stock_pct=0.15&lead_time_weeks=2` — recomputed stock plan

**XAI**
- `GET /api/explain?store=1` — SHAP contributions for a store's next-week forecast

**RAG**
- `POST /api/ask` — body `{"question": "..."}` → grounded answer + cited document sections

**Agentic AI**
- `POST /api/agent` — body `{"store": 10, "lead_time_weeks": 2}` → forecast + inventory + supplier + policy → reorder decision with explanation

**Automation**
- `GET /api/alerts` — latest alert sweep (runs one if none exists yet)
- `POST /api/alerts/run` — trigger a fresh sweep across all stores immediately

## How forecasting beyond the dataset works

**XGBoost** needs lag (1/4/8/12 week) and rolling (4/8/12 week) sales
features, which don't exist for future dates, so `/api/forecast` forecasts
**recursively**: predict week 1, feed that prediction back in as
`sales_lag_1` (and into the rolling windows) to predict week 2, and so on.

**LSTM** works the same way at a sequence level: it keeps a rolling 12-week
window of raw features, predicts the next week, appends that prediction to
the window, drops the oldest week, and repeats.

Both carry forward exogenous variables (temperature, fuel price, CPI,
unemployment, holiday flag) from the last known value unless you override
them on the Forecast page. Accuracy degrades gradually as the horizon grows
— treat forecasts beyond ~8 weeks as directional (see `store_guidelines.md`).

## About the "inventory" numbers

This dataset is **store-level weekly sales**, not a live inventory/POS feed.
The Stock Plan, Explain, Alerts, and Agent all need *some* notion of current
inventory to reason about reorders, so `app/inventory_utils.py` derives a
deterministic, store-seeded estimate from recent demand — clearly documented
as simulated (see `data/knowledge_base/product_information.md`, which the RAG
assistant will tell you about if asked). Swap `get_inventory()` for a real
POS/inventory API call and every downstream feature (stock plan, agent,
alerts) keeps working unchanged, now against real numbers.

## Optional: LLM-generated answers

By default, the RAG assistant and the agent's explanations are produced
**deterministically** — template-stitched retrieved text for RAG, and
rule-based narrative for the agent (see `agent._explain()`). This means the
app is fully functional and reproducible with zero external API calls.

If you set an `ANTHROPIC_API_KEY` environment variable, both `rag_utils.py`
and `agent.py` will additionally call the Anthropic API to phrase the answer
more naturally — but strictly grounded in the same retrieved
documents/computed numbers, never inventing new ones. Unset the variable (or
leave it unset) to fall back to the deterministic path.

```bash
export ANTHROPIC_API_KEY=sk-ant-...   # optional
```

## Automation scheduling

`app/automation.py` starts a background job (via `APScheduler`) that runs
the full agent sweep daily at 08:00 server time and writes results to
`model/alerts.json`. If `APScheduler` isn't installed or fails to start, the
app still runs fine — just trigger `POST /api/alerts/run` manually (the
Alerts page's "Run check now" button does exactly this).

## Deploying

The built-in Flask dev server (`python3 app.py`) is fine for local use or a
quick demo, but isn't meant for production traffic. To deploy for real:

```bash
pip install gunicorn
cd app
gunicorn -w 2 -b 0.0.0.0:8000 app:app
```

Use fewer workers than you might expect (`-w 2`, not `-w 4+`) since each
worker loads its own copy of the XGBoost + LSTM + SHAP models into memory.
Put it behind Nginx or a platform like Render, Railway, Fly.io, or a VM, and
set `FLASK_DEBUG=0` (the default) in production.

## Retraining on new data

Nothing here is hard-coded to the 2010–2012 window — re-running
`scripts/preprocess.py`, `scripts/train.py`, and `scripts/train_lstm.py`
against an updated `Walmart.csv` (same column schema) retrains and
re-exports everything the app needs, no code changes required.
