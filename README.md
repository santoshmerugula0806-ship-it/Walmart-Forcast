# WM-Forecast — Walmart Weekly Sales Forecasting Console

A full working web app built on top of the model from `Walmart_Data_Preprocessing.ipynb` and
`Walmart_Model_Training.ipynb`. It retrains the same pipeline (Naive baseline, Linear Regression,
Random Forest, XGBoost — XGBoost wins with ~3.6% WAPE), then serves it through a Flask backend
and a 6-page interactive frontend.

## What's inside

```

├── data/
│   └── Walmart.csv              ← your raw dataset (already included)
├── scripts/

│   └── train.py                 ← reproduces the training notebook, exports the model
├── model/                       ← generated by train.py (trained model + metrics)

│   ├── app.py                   ← Flask app: pages + JSON API

│       └── vendor/chart.umd.js  ← Chart.js, self-hosted (no CDN dependency)

```

## Setup

Requires Python 3.10+.

```bash
cd walmart-forecast-app
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

## 1. Build the model (run once, or whenever Walmart.csv changes)

```bash
python3 scripts/preprocess.py   # -> data/train_features.csv, test_features.csv, full_features.csv
python3 scripts/train.py        # -> model/best_model.joblib + metrics files
```

You should see the same numbers as the notebooks:

## 2. Run the app

```bash
cd app
python3 app.py
```

Open **http://localhost:5000** in your browser.

To retrain with a new/updated `Walmart.csv`, drop the new file into `data/Walmart.csv` and re-run
step 1 — the running app will pick up the new model on restart.

## Pages

| Page | Route | What it does |
|---|---|---|
| Overview | `/` | Landing page, model scorecard |
| Dashboard | `/dashboard` | Portfolio-wide trends, holiday effect, model comparison, feature importance |
| Store Log | `/stores` | Per-store sales history + actual-vs-predicted accuracy for all 45 stores |
| Forecast | `/forecast` | Live 1–26 week forward forecast for any store, with optional what-if overrides (holiday flag, temperature, fuel price, CPI, unemployment) |
| Stock Plan | `/stock-plan` | Recommended stock per store from forecasted demand + adjustable safety-stock % and lead time |
| Model | `/about` | Full methodology, metrics, feature importance table, known limitations |

## API (used by the frontend, also usable directly)

- `GET /api/model-metrics` — model comparison table + metadata
- `GET /api/feature-importance` — importance per feature
- `GET /api/actual-vs-predicted` — test-period actual vs predicted, aggregated by week
- `GET /api/holiday-effect` — avg sales holiday vs non-holiday
- `GET /api/stores` — list of all stores with summary stats
- `GET /api/stores/<id>/history` — full sales history for a store
- `GET /api/stores/<id>/actual-vs-predicted` — test-period accuracy for a store
- `GET /api/stores/<id>/latest-state` — most recent known feature row for a store
- `POST /api/forecast` — body `{"store": 1, "weeks": 4, "Holiday_Flag": 1, "Temperature": 55, ...}` (overrides optional) → recursive multi-week forecast
- `GET /api/stock-plan?safety_stock_pct=0.15&lead_time_weeks=2` — recomputed stock plan

## How forecasting beyond the dataset works

The model needs lag (1/4/8/12 week) and rolling (4/8/12 week) sales features, which don't exist
for future dates. The `/api/forecast` endpoint starts from each store's last known state and
forecasts **recursively**: it predicts week 1, feeds that prediction back in as `sales_lag_1` (and
into the rolling windows) to predict week 2, and so on. Exogenous variables the model can't know
in advance (temperature, fuel price, CPI, unemployment, holiday flag) are carried forward from
the last known value unless you override them on the Forecast page. This means accuracy degrades
gradually as the horizon grows — treat forecasts beyond ~8 weeks as directional.

## Deploying

The built-in Flask dev server (`python3 app.py`) is fine for local use or a quick demo, but isn't
meant for production traffic. To deploy for real:

```bash
pip install gunicorn
cd app
gunicorn -w 4 -b 0.0.0.0:8000 app:app
```

Then put it behind Nginx / a platform like Render, Railway, Fly.io, or a VM, and set `FLASK_DEBUG=0`
(the default) in production.

## Retraining on new data

Nothing here is hard-coded to the 2010–2012 window — re-running `scripts/preprocess.py` and
`scripts/train.py` against an updated `Walmart.csv` (same column schema) will retrain and
re-export everything the app needs, no code changes required.
